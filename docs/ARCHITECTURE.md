# How Aerilo works

This explains the code to someone who has never opened it. Read it top to bottom once; after that the section headings are a map. [DEVELOPING.md](DEVELOPING.md) covers building, testing and releasing.

## The idea in one paragraph

Aerilo is one button, **Breathe**. On a Mac it measures the system, clears caches that rebuild themselves, and lists what is slowing the Mac down, with Apple's on-device model choosing what to mention first. On iPhone, iPad, Apple TV and Vision Pro, where no app may see or manage other apps, the same button tidies the photo library instead. Everything Aerilo does is written to a log the user can read and export. Nothing leaves the device.

The two Mac targets compile the same sources. They differ in entitlements (`Config/`) and in one compile flag, `AERILO_DIRECT`, which only switches on the update check. Everything else that differs between them is decided at run time by `Env.isSandboxed`.

There are two widget targets only because a widget's bundle id must start with its app's id. The widget is embedded on macOS and iOS; tvOS and visionOS builds leave it out.

The Xcode project file is generated by `scripts/make-project.py`. Each target follows its folders, so adding a Swift file needs no project change. Edit the script, not the `.pbxproj`.

## The Mac app

### State: `AppModel`

`AppModel` (`Engine.swift`) is the single source of truth, an `@Observable` class on the main actor. Views read it from the environment. It holds the latest `SystemSnapshot`, the process list, the cleanable items with their sizes, the findings, the advice, the current `BreathPhase`, and the `steps` text shown under the orb.

A background loop calls `refresh()` every 10 seconds (every 3 while the Activity screen is open or a breath is running). `refresh()` does the sampling off the main thread and assigns the results back.

### Measuring: `SystemProbe.swift` and `Probes.swift`

- **`SystemProbe`** reads memory (`host_statistics64`), memory pressure and swap (`sysctl`), processor load (tick deltas), free storage (`statfs`), thermal state, uptime and total network traffic (`getifaddrs`). `SystemSnapshot.health` turns these into a score out of 100; `healthReasons` lists what lowered it, using the same arithmetic, so the number is always explainable.
- **`ProcessProbe`** lists the user's processes and reads each one's memory and processor time. It tries `proc_pid_rusage` first, which gives the "memory footprint" Activity Monitor shows. Inside the App Store sandbox that call only answers for Aerilo itself, so the probe falls back to `proc_pidinfo(PROC_PIDTASKINFO)`, which the sandbox does allow and which gives resident memory (slightly lower, because it leaves out compressed pages). It keeps a short history per process to detect two patterns:
  - **stuck**: above 90% of a core for 60 seconds without a break;
  - **memory growing**: at least 4 minutes of samples, +150 MB and +25%, with 80% of steps not falling. A leak can't be proven from outside a process; this is the visible sign of one.
- **`NetworkProbe`** runs the system tool `nettop` for per-app traffic. The sandbox cannot run it, so this is empty in the App Store edition.

### Findings: `Rules`

`Rules.build` (`Engine.swift`) is a pure function from measurements to a list of `Finding`s: stuck apps, growing memory, heavy apps when memory is tight, low storage, large rebuildable caches, heavy swap, heat, long uptime, many login items, a waiting macOS update. Each finding has a severity and, where it makes sense, one action. Helper processes are added up under the app they belong to (`Rules.groups`), which is how people think about "Chrome".

Aerilo never offers to quit the apps in `Rules.protected`.

### Cleaning: `Cleaner.swift`

`Cleaner.items()` is the catalogue of what can be cleared, in three tiers:

1. **safe**: cleared by Breathe (Xcode build data, npm, Yarn, Homebrew and pip caches, app-update leftovers; in the direct edition also unusable simulators, the Chrome signing copy and test-runner leftovers);
2. **rebuildable**: the user ticks these (CocoaPods, Gradle, iOS device support, unused simulator versions);
3. **ask**: shown with "Reveal", never deleted (Xcode archives, the Chrome profile).

Three mechanisms keep deletion safe, and all three must agree before anything is removed:

- **Blockers.** Each item has a closure that returns why it must be skipped right now, for example "Xcode is running". Skips are shown and logged.
- **The guard.** `Cleaner.isSafeTarget` refuses any path that is not inside a short list of known cache locations, at least two folders below the home folder, or inside the per-user temp area. It is checked at the moment of deletion, whatever the catalogue says.
- **Tools, not `rm`, where a tool exists.** Simulators are only removed with `xcrun simctl`.

A folder that is itself a symlink is never emptied, and a symlink inside a cache is removed without following it.

### What keeps a clean-up from going wrong

- **The one button is narrow.** Breathe clears only the always-safe items that are still ticked in Storage. Simulators, other apps' caches and build caches wait for the user. "Caches of closed apps" lists only folders named like an app identifier, because other folders under Caches can hold things that do not rebuild themselves. The Siri and Shortcuts action opens the app and asks first.
- **Asked at the last moment.** Each item's `blocker` gets a fresh list of processes immediately before that item is cleared, and "Caches of closed apps" checks each folder's app again (`inUse`) as it reaches it. A tool that starts in the instant between the question and the removal can still lose cache files; they are caches.
- **Removal through an open handle.** `Cleaner.remove` opens the folder once (refusing a link), asks the system where that handle really is, checks that place with `isSafeTarget`, and then removes by name relative to the handle. Swapping the folder or a parent for a link after the check cannot redirect it. Links inside are removed, never followed; other volumes are never entered.
- **The temp area is exact.** Only below this user's own `T` and `X` folders, as macOS reports them.
- **Commands always return.** `Shell.run` starts the tool in its own process group and reads with a deadline; when time is up the whole group is asked to stop, then killed.
- **A pid is not an identity.** Every process is remembered with its start time (`ProcInfo.born`). Quit, end and show check that the pid still belongs to that process and refuse otherwise (`action.refused` in the log).

### The Breathe sequence

`AppModel.breathe()` runs these steps, writing a line to `steps` and to the log at each one:

1. sample the system and processes;
2. measure every cleanable item;
3. sample again, so processor figures cover a real interval;
4. clear the tier-1 items that are not blocked, one at a time, and measure what was actually removed;
5. build the findings;
6. ask `Advisor` for an order and a reason per finding;
7. move the orb from inhale to exhale to done.

It never quits an app. Quitting is always a separate click on a finding or in Activity. In the App Store edition, which is not allowed to quit other apps, the click brings the app forward instead.

### The assistant: `Advisor.swift`

`Advisor.plan` sends the measurements and the list of findings to `SystemLanguageModel` (Apple's on-device model, FoundationModels framework) and asks for a `ModelPlan`: a headline and an ordered list of finding ids with one reason each. The answer is validated: unknown ids are dropped and missing findings are appended. The model can reorder and explain; it cannot add an action. When the model is unavailable, `Advisor.rules` produces the same structure from severities.

Every model call goes through `Timeout.run`, which returns on time even if the model never answers. (A task group cannot do that: it waits for a stuck child. This was a real bug, found by the simulator tests.)

`BreatheIntent` and `HealthIntent` expose Breathe and the health reading to Siri, Spotlight and Shortcuts.

### Looking inside an app: `Insights.swift`

Browsers built on Chromium and apps built on Electron (VS Code, Slack and many more) run as dozens of processes, and each one says what it is on its command line (`--type=renderer`, `--extension-process`, a path under an editor's extensions folder). `Insights.build` collects an app's processes and everything they started, `Insights.classify` names each one, and the result is an `AppInsight`: sections such as "Tabs and windows", "Extensions" and "Language tools and tasks", heaviest first. `classify` is a pure function so the self-test can check it.

Aerilo reads those labels only. It cannot read tab titles, pages or documents, so tabs are numbered by size. Only tabs and tools can be ended from here, because the app reloads or restarts them; in the App Store edition the list is for reading. `Advisor.explain` asks the on-device model for one sentence about an insight, with `AppInsight.summary` as the fallback.

### Large files: `LargeFiles.swift`

Lists files of 200 MB and up in Downloads, Documents, Desktop and Movies. It is a separate button in Storage, not part of Breathe. Nothing is pre-selected, and the only action is moving a file to the Trash, one click per file, logged.

### The widget: `AeriloWidgets/`

One widget, small and medium. On the Mac it shows the health score, memory and free storage from `SystemProbe`; on iPhone and iPad it shows free storage and memory in use, the readings iOS allows. `StatusWidgetView` in `Shared/WidgetViews.swift` draws it, so the app can render the same view for screenshots. The widget only reads; it shares no data with the app and needs no app group.

### Permissions, notifications, updates: `Services.swift`

- `Permissions` checks Full Disk Access and manages opening at login.
- `Notifier` sends at most one low-space or low-memory notification every six hours. It never cleans.
- `Updater` (direct edition only) fetches `https://aerilo.app/appcast.json` once a day, compares versions, and offers the download. It only accepts links to aerilo.app or to this repository's GitHub releases, and never installs anything itself.

### Sandbox differences in one place

| | `AeriloDirect` | `Aerilo` (App Store) |
|---|---|---|
| Per-app memory and processor | footprint | resident size (fallback call) |
| Stuck and growing-memory detection | yes | yes |
| Quit another app | yes | no: "Show" brings it forward |
| Look inside an app | see the parts and end one | see the parts |
| Per-app network | yes (`nettop`) | no: the tool cannot run |
| Caches in the home folder | yes | after the user allows the folder (security-scoped bookmark) |
| Chrome signing copy, test leftovers | yes | after the user allows the temp folder |
| Simulators, simulator versions | yes (`simctl`) | no: the tool cannot run |
| Update check | yes | the App Store does it |

These were established by running a probe inside the sandbox, not from documentation.

## Photo tidying (all platforms)

`PhotoScanner.scan` (`PhotoEngine.swift`) reads the library and returns groups; it never changes anything.

- **Exact duplicates**: assets with the same type, pixel size, capture second and duration are candidates; they are duplicates only if their stored bytes hash to the same SHA-256. That holds for videos too: a video is read in pieces and hashed, and only when another video in the group has the same file size. An asset whose bytes are not on the device is never called a duplicate.
- **Similar shots**: photos taken within 5 seconds of each other with the same pixel size form a chain; neighbours in a chain are compared with `PhotoScanner.alike`. That uses Apple's image feature print when the device provides it (distance below 0.15; measured 0.03 to 0.04 for the same shot a second later and 0.23 and up for different pictures), and otherwise a 64-bit difference hash (at most 8 bits apart).
- **Old screenshots**: the screenshot subtype, older than 30 days.

Each asset appears in one category only, the first that claims it. Ticks are kept by asset id, so an asset listed twice would arrive ticked in a list that says nothing is ticked.

- **WhatsApp media**: recognised by the file name WhatsApp gives what it saves. Listed, never pre-selected. An app cannot open another app's storage on iOS, so this covers what WhatsApp saved to the library, not what is inside WhatsApp.
- **Screen recordings**: the screen-recording subtype. Never pre-selected.
- **Largest videos**: over 50 MB, largest first. These are never pre-selected.

Sizes come from documented calls only (`requestImageDataAndOrientation`, `requestAVAsset`), with network access off, so a scan never downloads from iCloud.

`PhotoModel` holds the groups and the set of ticked ids. `deleteSelected(in:)` calls `PHAssetChangeRequest.deleteAssets`; the system asks the user to confirm, and items go to Recently Deleted for 30 days. `PhotoAdvisor` gives the on-device model only counts and category names and asks for one sentence.

The Mac shows this in a Photos section with its own button (`PhotosView`); it is not part of Breathe, so the one tap never asks for the photo library. `AeriloMobile/MobileApp.swift` is the device app: the orb, a Device screen, and the log. `MobileIntents.swift` gives Siri and Shortcuts two actions: one opens Aerilo and starts a look through the library, the other says how much storage is free. Neither deletes anything.

## The log: `Audit.swift`

One JSON object per line in `~/Library/Logs/Aerilo/audit.jsonl` (inside the container in sandboxed builds). Each entry stores the SHA-256 of the entry before it, so editing an entry, or removing one from the middle, breaks the chain and `Audit.entries()` marks it. The newest entry's hash is also kept in the app's settings, apart from the file, so a log cut short at the end or replaced is noticed (`Audit.cutShort`). This is a consistency check, not a seal: someone who rewrites the file and the setting can make a log that passes. `Audit.title` turns an entry into a sentence; `Audit.report` produces the exported text file. To log something new, call `Audit.record("event.name", [...])` and add a case to `Audit.title`.

Command-line flags, all read through `Env`:

| `--demo` | sample data everywhere; nothing is read or deleted |
| `--capture --shot <screen>` | (Mac) open one screenshot window in demo mode |

| `--caption <text>` | (devices) one large line for App Store search screenshots |
| `--selftest` | (Mac) print what this build can do; deletes nothing of the user's |
| `--breathe-test` | (Mac) run the real Breathe sequence on a stand-in home folder |
| `--home <folder>` | (Mac) use a stand-in home; Aerilo then works only inside it |
| `--autobreathe` | (devices) start a scan at launch |

## Design rules worth keeping

- At rest the interface does not animate. A constantly moving glass surface cost about 18% of a processor core; the orb is still until a breath starts.
- No keyboard shortcut starts a clean-up. A stray Return once did.
- The interface says what it is doing while it does it, and the log says it afterwards.
- A failed lookup must never read as "nothing uses this" (see `Cleaner.unusedRuntimes`).
